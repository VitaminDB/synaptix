# NPU в synaptix

Рецепты запуска, отладки и расширения. Платформа телефона (CDSP, служба synnpu-qnn, установка) —
`synmobile/docs/19-cdsp-npu.md`.

## Устройство

```
модель (Tensor API) ── Device::Npu ── synaptix-kernels-npu: запись графа, сегменты, CPU для недостающего
                                          │
                                          ▼
                       synaptix-npu: общий IR (Graph) → профиль модели NPU → драйвер производителя
                                          │ qualcomm: перевод в QNN, соединения (PD), буферы dma-heap
                                          ▼
                       synnpu-qnn (демон, bionic) — по процессу на соединение, сборка в дочернем процессе
```

| Крейт | Что в нём |
|---|---|
| `synaptix-core` | `Device::Npu`, `Storage::Npu(NpuBuf)`, `Backend::upload/download`, `with_param_upload` |
| `synaptix-kernels-npu` | бэкенд `Device::Npu`: ленивая запись, представления, сегменты, CPU-путь |
| `synaptix-npu` | `Npu`/`CompiledGraph`/`NpuBuffer`, IR `Graph`, `models.rs` (профили), `qualcomm/` (драйвер и демон) |

Модели не портируются: всё, что идёт через Tensor API, попадает на NPU. Чего нет в переводе — считает CPU
(`synaptix-kernels-cpu`) на тех же данных.

### Как работает ленивая запись
- Операция на `Device::Npu` не считается, а записывается: выход — значение `Pending`. Выход Tensor-операции
  выделяется `alloc_uninit` и заполняется вызовом `Backend::…(src, &mut dst)` — так и записывается узел.
- При чтении (`to_device(Cpu)`, `to_vec*`) записанная цепочка режется на сегменты и исполняется; выходы
  сегмента — значения, нужные дальше по цепочке или удерживаемые снаружи (счёт ссылок `Arc`).
- Представления (reshape/permute/narrow/broadcast) переводятся в reshape → strided slice → transpose → tile;
  если раскладка не укладывается в эту схему — gather по таблице индексов.
- Приведение типа и копия **готовых** данных (не из графа) считаются сразу на CPU: так `to_dtype` весов при
  загрузке не превращается в узлы графа.
- Веса, загруженные загрузчиками synaptix (`SynBundleLoader`, `SafetensorsLoader`, `StreamingLoader`), помечаются
  `with_param_upload` и вшиваются в граф статикой; всё остальное — входы графа. Граф без входов HTP не собирает,
  поэтому данные статикой не становятся никогда.
- Кэш: в процессе — по хэшу структуры графа; на диске демона — context binary по ключу
  `ключ#хэш IR#вариант перевода` (вариант = модель NPU + нормы + уровень оптимизации + предмасштаб).

## Запуск

```sh
synaptix devices                                       # npu:0 Hexagon HTP v69 (qualcomm-htp-v69), SoC 42, …
synaptix transcribe whisper.syn речь.wav --device cpu --encoder-device npu   # энкодер на NPU, декодер на CPU
```

Из кода:
```rust
let info = synaptix_kernels_npu::register()?;          // открыть NPU, зарегистрировать бэкенд
let dev = Device::Npu(0);
let w = WhisperWeights::open(path, dev, DType::F16)?;  // веса — статикой в граф
let y = enc.forward(&mel.to_device(dev)?.to_dtype(DType::F16)?)?;
let host = y.to_device(Device::Cpu)?;                   // здесь граф уходит на NPU
```

- Тип вычислений на NPU — F16 (BF16 HTP не умеет: такие операции уйдут на CPU).
- Раздельные устройства в модели: `WhisperPipeline::from_syn_split(path, Cpu, F32, Npu(0), F16)`.
- Режимы: `--device npu` — всё возможное на NPU, остальное на CPU; раздельный — по компонентам; `cpu` — как раньше.

### Пошаговый декодер на NPU
Граф должен быть одинаковым на каждом шаге, иначе каждый токен — новая сборка. Рецепт — device-путь с
фиксированными формами (тот же, что для CUDA-graph): KV-буфер выделен на `max_target`, позиция и длина — тензоры
(`write_host_u32` на NPU загружает новое значение — вход графа).
- `kv_append_dev` → `buf + onehot(pos)·(k − buf)`, onehot = clamp(1 − |iota − pos|, 0, 1), `iota` — статика 0..cap−1;
  весь буфер — выход шага и вход следующего (без копий через CPU).
- `flash_attention_dev` → маска `(clamp(t − iota, 0, 1) − 1)·60000` к scores, Softmax, MatMul.
- Изменение тензора на месте записывается со «снимком» старой версии (`record::snapshot`): узел читает снимок,
  тензор получает новую версию.
- `embed_gather` → Gather (индексы U32 → I32 в графе).
- Whisper: `decode_segment_dev` — на `Device::Npu` декод идёт так; `--device npu` — весь Whisper на NPU.

### Модели с переменной длиной входа (wav2vec2 / WavLM, synspeak)
Речевые кодировщики без фиксированного окна: каждая длина записи — новая форма графа и новая сборка
(20–60 с). Рецепт (`Wav2Vec2Ctc`):
- **Корзины длины** — на `Device::Npu` вход дополняется тишиной до ближайшей из 2/4/8/12 с
  (`length_buckets()`), лишние кадры отрезаются после модели (`frames_for`); `SYNAPTIX_LEN_BUCKETS=0/1`.
- **Веса — статика**: загрузчик модели оборачивает `Tensor::from_raw_slice` в `with_param_upload`; с
  весами-входами сборка 230 с и исполнение 350 мс, со статикой — 29 с и 78 мс (0,5 с речи, v69).
- **Кэш графов с вытеснением** (`synaptix-kernels-npu::record::GraphCache`): каждая корзина — свой набор
  контекстов с копией весов (~600 МБ у large на диске `/var/cache/synnpu` и в PD), поэтому в памяти
  держатся графы на `SYNAPTIX_NPU_RESIDENT_MB` (½ `session_bytes`), давно не использованные
  отпускаются (`Drop` → `GRAPH_FREE` демона). Контекст кладётся в первый PD со свободным местом. Без этого четвёртая корзина не помещалась в 4 PD; у корзины 15 с сегмент внимания требовал ~700 МБ в PD, поэтому предел — 12 с.
- **Прогрев**: `synspeak-cli warmup --device npu` собирает графы всех корзин один раз (4 корзины — 2,5 мин);
  приложение делает то же в фоне между заданиями.
- `Backend::cat` (умолчание — байты CPU; NPU — узел `Concat`), `index_select` на NPU — через CPU: раньше
  любое не-CPU устройство считалось CUDA и падало на `cudarc` без `libcuda`.

Замеры wav2vec2-large (synspeak, HTP v69): оценка фразы 0,7 с в новом процессе (из них ~0,4 с — открытие
5 контекстов из кэша) против 1,3–2,1 с на CPU; оценки совпадают с CPU в пределах 1–3 баллов.

## Предкомпиляция графов на ПК
Сборка графов большой модели на телефоне долгая (turbo — ~2 мин один раз). На ПК: x86 QAIRT, офлайн-демон
(`build.sh --host`, `SYNNPU_OFFLINE=1 SYNNPU_SOC=42 SYNNPU_ARCH=69`) готовит context binary тех же ключей;
исполнение пропускается (выходы — нули). Запускать **ту же команду, что и на телефоне**: граф зависит от кода
вокруг модели (например, приведение выхода к F32 на NPU или на CPU — разные последние сегменты).
```sh
synmobile/hw/npu/npu-precompile.sh transcribe whisper.syn речь.wav --device cpu --encoder-device npu
```
Скрипт докладывает на телефон недостающие графы (`/var/cache/synnpu`). Turbo: 25 сегментов на ПК за 64 с,
на телефоне — 25 «открыт из кэша», ни одной сборки.

## Квантованные веса на NPU (int8)
Пробник `cargo run -p synaptix-npu --example npu_quant_probe` (офлайн-демон на ПК, HTP v69, QAIRT 2.42):

| Граф | Результат |
|---|---|
| FullyConnected, x F16, вес F16 2048×2048 | собран, контекст 8,2 МБ |
| FullyConnected, x F16, вес I8 с поканальными шкалами (`Quant::Axis`) | собран, контекст 4,2 МБ — веса остаются int8 в контексте |
| FullyConnected, x F16, вес I8 с одной шкалой (`Quant::Tensor`) | собран, 4,1 МБ |
| I8 → `Dequantize` → F16 → FC | **не собирается**: «Op Dequantize does not support per-channel quant tensor» |
| I4 (`Quant::Axis`) | профиль `qualcomm-htp-v69` отклоняет (`weights` без I4); на HTP не проверено |

Значит, рецепт для v69 — int8-веса по каналу прямо во входе FullyConnected/MatMul с F16-активациями; память
контекста и PD уменьшается вдвое против F16. Инфраструктура: `Quant` в `TensorDesc`, протокол демона
(`SYNNPU_QUANT_AXIS_SCALE_OFFSET`), `Op::Dequantize` в IR (`SYNNPU_DEQUANT_OP` — имя QNN-оп для экспериментов).

Осталось:
1. В `synaptix-kernels-npu` — `Backend::linear_quant`: из `QuantWeight` (SQ/ggml/NVFP4/MXFP8) построчно деквантовать
   на CPU (`synaptix_kernels_cpu::quant::dequant::WeightView`), переквантовать симметрично в int8 по строке, положить в
   `NpuBuffer` один раз на вес (кэш по указателю packed) и записать `NodeOp::LinearQuant` со шкалами в `Quant::Axis`.
2. Попробовать I4 на v69, добавив `DType::I4` в `weights` профиля; для SQ2/SQ3 — хранить как I4 (у HTP нет 2/3 бит).
3. Политика на `Device::Npu`: как CPU-профиль, но счёт F16 (`optimal_profile_for_device` сейчас отдаёт CPU-профиль
   для всех не-CUDA устройств).
4. Статическое квантование активаций (UFIXED8/16 + калибровка) — отдельный этап, если int8 по весам не хватит.

### Формат q8row: подготовка весов (готово)
`DType::Q8Row` — int8 по выходному каналу: `.qpacked` = i8 `[N, K]` сплошняком (так его берёт FullyConnected HTP без
перепаковки), `.qscales` = f32 `[N]`, раскладка `syn-quant-v1` (`format = "q8row"` в `quant_manifest.json`).
На CPU/CUDA веса деквантуются при загрузке, на `Device::Npu` модель получает `QuantWeight` и вызывает `linear_quant`.

Рецепт (wav2vec2/WavLM):
```sh
synaptix calibrate model.syn <каталог WAV> -o model.calib --limit 256      # E[x²] входов каждого Linear
synaptix quantize model.syn model-npu.syn --format q8row --device cpu --calib model.calib
```
Шкала строки подбирается перебором порога отсечения (0,6…1,0 от absmax, 40 шагов) по ошибке **выхода** слоя
Σₖ E[xₖ²]·(wₖ−ŵₖ)². Без `--calib` — absmax: MSE по самим весам хуже absmax (обрезает редкие крупные веса, а они
важны). `lm_head` и стопки `[E,N,K]` (у wav2vec2 это pos_conv) остаются F16. Квантование — на CPU, секунды.

Замеры w2v2-lv60-espeak (эталон — F16-веса со счётом F32 на CUDA; пример `quant_parity` крейта wav2vec2):

| Вариант (счёт F16) | KL, нат/кадр | argmax | расхождение фонем |
|---|---|---|---|
| F16-веса | 0,00002 | 99,98 % | 0,00 % |
| q8row, MSE по весам | 0,00177 | 99,68 % | 0,87 % |
| q8row, absmax | 0,00084 | 99,78 % | 0,47 % |
| q8row, калибровка (256 записей speechocean762 train) | 0,00068 | 99,82 % | 0,40 % |

Почти вся ошибка — в MLP (только MLP в int8: KL 0,00082). Итоговая метрика synspeak на speechocean762 test
(PCC с экспертами, фонема/слово/фраза): F16 0,5381/0,5091/0,6492, q8row 0,5377/0,5086/0,6498 — без потерь.
Размер весов 0,60 → 0,30 ГБ.

Остальные модели synspeak (расхождение фонем с эталоном F32; F16 / q8row): wavlm-en — 0,14 % у q8row;
w2v2-kk — 0,07 % / 0,71 %; wavlm-kk — 0,22 % / 0,22 %. Казахские калибровались на записях курса synspeak (других
казахских записей под рукой нет), на них же и проверены.

### q8row на NPU (готово, проверено офлайн-демоном)
`Backend::linear_quant` NPU-бэкенда принимает `QuantWeight` формата q8row с F16-активацией и пишет узел
`NodeOp::LinearQ`: упакованные i8 (параметр модели в `NpuBuffer`) становятся весом FullyConnected `I8 [N, K]` с
`Quant::Axis { axis: 0, (scale, 0)×N }` через `Graph::weight_buffer_quant`; шкалы читаются с хоста один раз на вес.
wav2vec2 на `Device::Npu` с q8row-бандлом идёт этим путём, на CPU/CUDA тот же бандл деквантуется при загрузке.

Офлайн-сборка (ПК, QAIRT 2.42, HTP v69) wav2vec2-large q8row, все корзины 2/4/8/12 с: 22 контекста, **1,3 ГБ**
(F16 — ~2,4 ГБ), 64 с. Команда `synaptix warmup <модель.syn>` прогоняет модель по всем корзинам; вместе с
`synmobile/hw/npu/npu-cache-build.sh <каталог> warmup <модель.syn>` — готовые графы для пакета.

Предсобранные графы из пакетов: демон ищет `<ключ>.bin` в своём кэше, затем в каталогах `SYNNPU_CACHE_RO`
(через `:`, по умолчанию `/usr/lib/synaptix/npu-cache`) — в самом каталоге и на один уровень вложенности
(`/usr/lib/synaptix/npu-cache/<модель>/<ключ>.bin`). Проверено: пустой кэш + RO-каталог — 22 «открыт из кэша», ни
одной сборки.

### OmniVoice (синтез речи) на NPU, int8 (готово)
Бэкбон (двунаправленный Qwen3, 28 слоёв) — q8row: `synaptix calibrate omnivoice.syn packaging/models/calib/tts.txt`
(синтез 24 фраз ru/en/kk, статистика входов слоёв) и `synaptix quantize … --format q8row --calib … --include
llm.layers.` (кодек и эмбеддинги — как были). Качество (9 фраз, Whisper turbo по синтезу): F32 — WER 5,4 % / CER 1,3 %,
q8row со счётом F16 — 7,5 % / 1,7 %; 16 шагов маскированного декода вместо 32 — без потери разборчивости.

На NPU: эмбеддинги и кодек HiggsAudio — на CPU, бэкбон — корзины длины 128/256/512 (добивка в конец, маска ключей
всегда, даже без добивки — один граф на корзину), cond и uncond — отдельными проходами B=1. Графы: 29 контекстов,
1,4 ГБ (`synaptix warmup omnivoice-npu.syn` через `npu-cache-build.sh`). Xiaomi 12T Pro, фраза 3,5 с, 16 шагов:
8,2 с (NPU 6,1 с — 32 прохода по ~190 мс, кодек на CPU 1,7–2,4 с); первый вызов после загрузки — 11,7 с.

## Отладка точности (рецепт с Whisper large-v3-turbo)
1. Эталон на CPU f32 (ПК): `encoder_npu model.syn cpu ref.f32` (пример `synaptix-asr-whisper`).
2. Сверка по строкам на телефоне: `encoder_npu model.syn npu out.f32 ref.f32` — худший/средний cos, max |Δ|.
3. Где ломается — по слоям: `LAYERS=n encoder_npu …` (`WhisperEncoder::forward_partial`) против эталонов
   `LAYERS=n` с ПК; бинарный поиск по n.
4. Какой узел — `layer_trace model.syn i вход.f32 строки`: слой i на CPU f32 и на NPU с одним входом,
   все промежуточные (ln1, q, k, v, attn, out, res1, ln2, fc1, gelu, fc2, res2).
5. Подать на CPU вход, посчитанный NPU (`layer_trace … npu_L.f32`): если CPU даёт то же — дело в накопленном
   отклонении FP16, а не в операции.
6. Отдельные операции на диапазоне значений — `npu_range` (Gelu/Sigmoid/Tanh, FC с выходом до 5000).

Найдено так: у turbo с 21-го слоя у токенов-«стоков» массивные активации (до ~280); FP16-отклонение за 20 слоёв
(cos 0,992–0,996 на этих строках) меняет их величину; сам слой на NPU совпадает с CPU (Δ 0,4 на 200).
Распознавание при этом совпадает с текстом слово в слово.

## Отладка сборки и памяти
- Граф не собирается — `SYNNPU_TRACE=1`, журнал демона (`journalctl -u synnpu-qnn`): QNN пишет оп и входы.
- Подозрение на сочетание операций — пробник `npu_probe` (отдельные маленькие графы).
- Память подготовки — строка «сборка: пик памяти» в журнале демона на каждый граф.
- Место в PD — «контекст …: N МБ, spill-fill M МБ (общий буфер группы)»; «Failed to find available PD» → драйвер
  сам откроет новое соединение (`PD_FULL`).

## Новая модель NPU или производитель
- Модель того же производителя: запись в `synaptix-npu/src/models.rs` (`arch`, SoC, типы активаций/весов,
  разрядности, `fused_norms`, `session_bytes`). Свойства проверять пробниками на устройстве.
- Производитель: модуль `synaptix-npu/src/<vendor>/` с `impl Npu` (alloc, compile → `CompiledGraph::run`) и
  переводом общего IR; добавить в `probe()` в `lib.rs`. Бэкенд `synaptix-kernels-npu` от производителя не зависит.

## Грабли (Hexagon HTP v69, QAIRT 2.42)
- **Память подготовки.** Подготовка QNN большого графа в одном процессе исчерпывает регионы scudo и память
  телефона (2026-10-10 телефон завис). Сборка — в дочернем процессе `synnpu-qnn --build` (`PREPARE_ONLY`),
  у службы `MemoryHigh/MemoryMax`, граф режется на сегменты.
- **PD ≈ 1,8 ГБ.** Контексты одного процесса не помещаются: turbo (1,3 ГБ весов) — на несколько PD (соединений);
  контексты одного соединения делят spill-fill (`REGISTER_MULTI_CONTEXTS`).
- **Attention.** Scores [20,1500,1500] раздувают spill-fill (692 МБ на слой) и подготовку (60 с, 1,7 ГБ); масштаб
  на Q и группы голов — 59 МБ, 5 с, 0,5 ГБ, и быстрее (tiny 104 → 67 мс).
- **Веса-входы** медленнее статики в 1,4–7 раз (GEMV 1×4096×4096: 0,84 → 5,7 мс).
- **LayerNorm/ReduceMean FP16** не собирались после длинных цепочек Reshape из представлений — цепочки
  сворачиваются, мёртвые узлы удаляются; после этого нативный LayerNorm работает и точнее разложенного.
- **Нормы в FP16:** сумма квадратов строки с выбросами переполняет FP16 — вход делится на 16 (`eps/256`), это точно.
- **Порядок в `match` с guard'ом мьютекса** (`match self.conn.lock().call(..)`) держит замок на весь `match` —
  вложенный вызов виснет; результат сначала в переменную.
- **`pkill -f строка`** в `ssh 'команда'` убивает и саму команду (строка совпадает) — `pkill -x имя`.

- Слитый `RmsNorm` QNN на HTP v69 не собирается («Selecting disabled op … QNN_RmsNorm») — всегда раскладывается на
  примитивы (`SYNNPU_FUSED_RMS=1` — вернуть слитый для опытов). `LayerNorm` слитый работает.
- Батч больше 1 на NPU даёт неверный результат (парный проход cond+uncond OmniVoice: argmax 1 % против 90 % у B=1) —
  пока все модели идут с B=1; причина не найдена.
- Запись на NPU ленивая: если записать два прохода подряд и только потом прочитать, граф режется на сегменты иначе,
  чем при прогреве, и предсобранные графы не совпадают (ключ — структура сегмента). Читать результат каждого прохода
  сразу; прогрев (`synaptix warmup`) должен повторять ровно ту же последовательность записи и чтения (включая
  приведение логитов к F32 и вывод hidden у CTC).
