# Inkling-2-Mini (thinkingmachines) — порт

Оригинал: `~/Storage/Нейросети/Модели/_hf/Inkling-2-Mini` (HF, 20 ГБ, не удалять).
Источники схемы: NVIDIA NeMo Automodel `components/models/inkling2` (PyTorch, с циклом),
llama.cpp `inkling2*.cpp`; transformers/vLLM/SGLang — только вариант без цикла.
Отдельной сверки с ними не держим: разовая проверка (жадное продолжение совпало),
дальше база качества — synaptix на исходных весах.

## Архитектура (text_config)

- 24 физических слоя, hidden 2304, словарь 201024 (без паддинга 200058), без RoPE.
- Цикл: слои `[6, 18)` проходятся 3 раза (48 применений слоёв); у каждого
  прохода свой KV и своё состояние свёрток (слоты кэша `24 + 2·12 = 48`).
  Проход p > 0 стартует с выхода пролога (слои 0–5) и его блоков; сообщения
  прошлого прохода (`bank` = его блоки после первого блока ядра + его выход)
  смешиваются запросами `msg_query[4]` (q, k, v, mlp) и вливаются в входы
  слоя контроллерами: `(1 − tanh(F·d))·x + tanh(G·d)·m`, `d = Down·[rms(x); rms(m)]`.
- Блочные attention-residuals (блок 6 слоёв): вход слоя — внимание по глубине
  `softmax(q · rms(states)/√H)` по выходам прошлых блоков и текущему потоку;
  первый слой блока начинает новый поток.
- Внимание: SWA 1024 (слои кроме 5, 11, 17, 23) и полное; 24 головы q, 8 kv, d 128.
  K/V через короткую каузальную свёртку k=4 с остатком (`(x + conv)/√5`), у полных
  слоёв — плюс динамические отводы от входа (`/√9`); у полных слоёв отдельные
  входы и нормы для q/k/v (3 запроса residual'а).
  q: L2-клип 22.63 после масштаба по голове; k: L2-клип; v: RMS-норма без веса.
  Позиции — относительный bias: `r = clip(Wr·x)` (16 на голову), таблица
  `r · proj[16, extent]` по расстоянию (0 вне `[0, extent)`), extent 1024.
  Полные слои: q и r × `tau = 1 + 0.1·ln(max(1, (pos+1)/8192))`.
  Синк на (токен, голову): `sink_proj·x` — лишний логит с нулевым value.
  Выход × `sigmoid(gate_attn·x)`, потом свёртка `attn_sconv` (k=4, `/√5`).
- MoE 128 экспертов, top-8, sigmoid + bias выбора, нормировка (eps 1e-20) × 8.
  Активация: `tanh(g/4)·4 · σ(g) · tanh(u/25)·25`. w13 в чекпойнте —
  строки gate/up ЧЕРЕДУЮТСЯ (2i — gate, 2i+1 — up). После MoE свёртка `mlp_sconv`.
- Выход: residual-смесь `output_query`, RMS-норма, unembed (отдельный от embed),
  softcap 30. Эмбеддинг × RMS-норма `embed_norm`.

## Веса

- Эксперты слоёв 0–19: NVFP4 modelopt — `w = e2m1 · e4m3(scale) · amax_e/2688`.
  97–99,9 % блочных масштабов в субнормалях E4M3 → в NVFP4 движка (без общего
  множителя) перекодировка теряет 5–7 % масштаба. Поэтому общий множитель
  `alpha_e = amax_e/2688` хранится отдельно и применяется: к выходу gate_up до
  активации, к весу маршрута — для down.
- Эксперты слоёв 20–23: MXFP8 (e4m3 + E8M0/32) — совпадает с MXFP8 движка бит в бит.
- Остальное BF16 (внимание, контроллеры), F32 (запросы residual'ов, роутер bias).
- `mtp.safetensors` — MTP/DFlash-голова (3 слоя + markov_head), `model.visual.*` — ViT 23 слоя.

## Цель качества

KLD к эталону и совпадение топ-токена не хуже unsloth при том же размере
(их KLD к UD-Q8_K_XL: Q4_K_XL 17.6 ГБ 0.0107 / 98.0 %; IQ3_XXS 11.7 ГБ 0.0269 / 94.7 %).

## Качество (KL к оригиналу, llm-eval-mix, 2048 токенов)

Рабочий бандл — `inkling2-mini-native.syn` (18,9 ГБ): веса оригинала без перекодировки,
KL 0,00002 (шум), top-1 100 %. Упаковщик умеет и реквант (`ink2_pack --mxfp8-experts/--attn/--head`),
замеры по группам: эксперты 20–23 → NVFP4: KL 0,0013 (−1,9 ГБ); голова → MXFP8: 0,0004 (−0,45 ГБ);
внимание → NVFP4: 0,014, → MXFP8: 0,005 (только веса: 0,0105 / 0,0042) — внимание держать в BF16.
Компактный бандл не делаем (решение пользователя).

## Скорость декода (RTX 5090 Laptop, нативный бандл)

21 → 79 ток/с (ёмкость кэша — по промпту): CUDA-граф шага (позиция и токен на карте), слитые ядра
контроллеров и роутера, слитые проекции внимания (q|r|gate|sink, k|отводы, v|отводы), внимание
split-K, смесь блоков в два прохода, top-k в варпе.

На 4K контекста (`ink2_long --ctx 4096 --gen 300`, медиана из 3) — **72,1 → 85,6 ток/с**, без смены
математики: KL к эталону 0,00001 (8192 токена, бит в бит). Префилл 4K — 1880 → 2225 ток/с.

- Выходы слитых BF16-проекций ядра читают срезами с шагом строки (`kern::cols`, флаг BF16):
  ушли приведение к F32 и 4–8 contiguous-копий на слой.
- Остаток потока влит в свёртки attn/mlp. Свёртки k и v идут одним запуском. Свёртка префилла
  считается блоком на токен плюс `ink2_conv_state`; раньше был последовательный цикл по T
  в 9 блоках, до 0,5 мс на чанк.
- Контроллеры q/k/v и их RMS — по одному запуску на этап (`blockIdx.z`, веса стопкой `[4, R, …]`).
  Роутер читает BF16, накопитель MoE обнуляет `ink2_route` (memset ушёл). Декод-внимание грузит
  K/V следующего ключа заранее. `ink2_route` для E ≤ 128 держит всё в регистрах.
- Движок (касается всех моделей с NVFP4): деквант E2M1 через аппаратный `cvt.rn.f16x2.e2m1x2`
  (sm_100a/120a, `SYN_ARCH_A`). Произведения e2m1·sc точны в f32, поэтому результат бит в бит
  прежний. Индексный GEMV экспертов (`tests/gemv_experts.rs`, формы Inkling): gate_up
  45,8 → 34,4 мкс (522 → 694 ГБ/с), down 21,9 → 14,9 мкс.

**Почему не 100.** nsys (`--cuda-graph-trace=node`, 4K, на токен, после изменений):

| | мс | |

| BF16 GEMV (проекции 48 × 54 МБ + unembed 0,93 ГБ = 3,53 ГБ) | 4,58 | unembed 861 ГБ/с, pa 810, wo/k/v 680–700 |
| эксперты NVFP4 (44 слоя) + MXFP8 (4) | 2,76 | NVFP4 ~680 ГБ/с в графе |
| внимание + сборка частей | 0,79 | |
| смесь блоков (2 ядра × 121) | 0,75 | |
| RMS (51 + в контроллерах) | 0,58 | |
| контроллеры (2 × 48) | 0,57 | |
| свёртки (146) | 0,46 | |
| маршрут, роутер, qkv, act и пр. | 0,70 | |
| итого ядер | ~11,2 | ещё ~0,6 мс зазоров между ~1050 запусками |

Обязательный трафик весов — 5,33 ГБ на токен. При 860 ГБ/с (лучшее, что даёт unembed) это 6,2 мс,
потолок ~160 ток/с даже при нулевой цене мелких ядер. Для 100 ток/с (10 мс) мелкие ядра и зазоры
должны уложиться в ~2,7 мс вместо ~4,9 сейчас. Опробовано и отброшено (замерено, медленнее или без
выигрыша):

- последний блок смеси сам делает softmax, выход и RMS: один запуск вместо трёх, но хвост
  последовательный — 12 мкс против 6 + 5,5;
- сборка частей декод-внимания последним блоком: 16,9 мкс против 13,2 + 3,0;
- 8 лейнов на строку у GEMV экспертов: в отдельном замере +15 %, в графе без выигрыша
  (84,0/82,4/82,4 против 84,0/83,8/82,3), к тому же порядок суммы другой.

Дальше остаётся то, что меняет порядок суммирования (шум ~0,002, см. ниже), или крупная
переделка: RMS в прологе GEMV, персистентное ядро цепочки смесь → контроллер → RMS, GQA-группировка
декод-внимания. Каждое из этого даёт 0,2–0,5 мс.

## Чувствительность к округлению

Любая смена порядка суммирования F32 внутри токена (смесь блоков, контроллер, роутер) даёт
KL ~0,002 между двумя одинаково точными реализациями: 48 маршрутизаций MoE на токен, выбор
эксперта на почти равных оценках переключается от последнего бита. Проверено: все исходные ядра
разом → KL 0,00002 к старому эталону; любое одно новое → ~0,002 в обе стороны; перплексия не
хуже (2,1993 против 2,2078). Порог «без потери качества» для этой модели — перплексия и KL
одного порядка с этим шумом, а не 0,00002. Отладочные переключатели старых путей
(`INK2_ORIG_MIX`, `INK2_OLD_CTRL`, `INK2_OLD_ROUTER` и др.) и их ядра (`ink2_mix_orig`,
`ink2_attn_orig`, `ink2_route_blk`, однопроходный `ink2_mix`) убраны после расследования: уборка
дала KL 0,00002 к эталону до неё (бит в бит). Сверка нового ядра с прежним — точечными тестами
ядер (`tests/attn_fa.rs`: `ink2_attn_fa` против `ink2_attn`).

## Vision (картинки 40–4096 px)

Код: `src/preprocess.rs` (препроцесс), `src/vision.rs` (башня, вставка в промпт), вход
`Inkling2Model::forward_with_embeds` (строки картинки встают после `embed_norm`, сами не
нормируются; длинный прогон режется по `MAX_CHUNK`, строки патчей — относительно всего прогона).
Пример: `ink2_vision <модель> <картинка>[,…] "<вопрос>" [--effort none] [--max-new N]
[--max-side 4096] [--max-tokens N] [--dump f.f32] [--tower-only]`. Бандл `ink2_pack` теперь
включает `model.visual.*` (BF16 как есть, +0,64 ГБ → 19,55 ГБ).

- Препроцесс (как `Inkling2ImageProcessor`): БЕЗ масштабирования — дополнение справа/снизу до
  кратного 40 px значением −1 по шкале 0…255, `x/255`, `(x−0.5)/0.5`; клетка 40×40 = один токен
  текста (4096² → 103×103 = 10 609 токенов). Альфа — на шахматку 204/153 (клетка 8 px).
  Сторона > 4096 (или сверх `--max-tokens`) уменьшается с сохранением пропорций — наше правило.
- Промпт: шаблон рендерит часть-картинку как `<|message_user|><|content_image|><|unused_200054|><|end_message|>`
  перед текстом пользователя; плейсхолдер разворачивается в rows·cols копий.
- Башня: патч 20×20×3 (порядок строка, столбец, канал) → линейная 1200→1024 без bias; сетка
  позиций 32×32, билинейно (align_corners=False, клэмп краёв) на сетку патчей; CLS
  (`class_embedding + cls_position_embedding`) в начале, позиция (0,0); патчи — (строка+1, столбец+1).
  `ln_pre`, 23 слоя pre-LN (`ln_1/ln_2`, LayerScale `ls_1/ls_2`, MLP GELU 4096), внимание полное
  по картинке, 16 голов × 64, осевой 2D RoPE на соседних парах каналов: первые hd/4 частот —
  столбец, следующие — строка, база 10000. Патчи идут клетками 2×2 → после башни 4 строки
  склеиваются в 4096 → `proj_in` 4096→4096, GELU, `proj_out` →2304.
- Реализация: остаточный поток F32, матрицы BF16, RoPE — `rope_interleaved_fused`, внимание —
  `flash_attention_bshd` (FA-2 split-Q, без матрицы скоров: 42 437 токенов 4096² помещаются).

Сверка с transformers (`modeling_inkling2.py`, CPU F32, вырезка vision-классов без правок
математики; признаки после merger): 40×40 — косинус 0,99998, отн. ошибка 0,59 %; 120×80 — 0,99995 /
0,78 %; 300×200 RGBA — мин. 0,99968 / 1,1 %; 640×480 — мин. 0,9952, средн. 0,99973 / 2,07 %;
4096×300 — мин. 0,9952, средн. 0,99975 / 2,05 %; 4096×4096 (эталон с SDPA вместо eager, CPU 7,6 мин) —
мин. 0,936, средн. 0,99941, cos < 0,99 у 0,33 % строк / 3,4 % (transformers в BF16 там же: мин. 0,917,
средн. 0,99843, cos < 0,99 у 1,8 % строк / 5,7 %). Для масштаба: сам transformers в BF16
против своего F32 на 640×480 — мин. 0,9927 / 3,6 %, т. е. наш порт ближе к F32, чем оригинал в BF16.

Время башни (RTX 5090 Laptop, после прогрева ядер): 640×480 — 0,03 с, 4096×300 — 0,07 с,
4096×4096 — 3,1–3,7 с. Первая картинка без прогрева платит ~12 с за сборку ядер NVRTC.
Префилл промпта 4096² (10 644 токена) — 10,6 с, 4096×3072 (7 953) — 8,2 с, декод после картинки 63–68 ток/с;
модель + башня (выгружается после кодирования) + KV на 10,6 тыс. токенов помещаются в 24 ГБ.

Ответы (жадно, `--effort none`): 40×40 красный круг — «A solid red circle on a white background»;
640×480 — три фигуры по цветам и порядку и надпись «HELLO 2026»; баннер 4096×300 — текст до места,
где он обрезан краем («…LAZY D», «likely DOG»); 4096×4096 — фигуры во всех четырёх углах, «SYNAPTIX»
в центре и полоса паддинга внизу; фото 4096×3072 — экран телефона в режиме загрузки с надписями.

## Длинный контекст и эксперты zero-copy

Эксперты бандла — 14,6 ГБ (слои 0–19 NVFP4, 20–23 MXFP8), остальные веса — ~4 ГБ; на карте
24 ГБ после весов свободно 19,6 ГБ. KV растёт только у 8 слотов полного внимания (32 КБ/токен
BF16): 200K — 6,5 ГБ, поэтому от ~100K контекста все эксперты уже не помещаются.

Режим выбирается при загрузке (`Inkling2Pipeline::load_with_ctx(path, dev, Some(ctx))`;
`load` — под `SYN_INKLING2_CTX`, по умолчанию 32K): если «эксперты + KV на ctx + запас на
активации» помещаются в свободную VRAM, эксперты остаются резидентными, как раньше. Если нет —
zero-copy:

- закреплённое зеркало стопок бандла в RAM (`mirror_ranges_natural`: NVFP4 в натуральной
  раскладке, масштабы тайловые; 14,6 ГБ за ~3 с из страничного кэша), загрузка ждёт его целиком;
- `ZcLayer` на каждый физический слой со своим dtype: три прохода цикла (слои 6–17) делят слоты
  одного слоя;
- пул слотов: свободная VRAM после весов − KV на ctx − запас на активации
  (`SYN_INKLING2_ACT_RESERVE_MB`, 1536) − место соседям (`SYN_INKLING2_ZC_HEADROOM_MB`, 512),
  делённая на байты слота всех 24 слоёв. При 200K выходит 98 слотов из 128 (11,2 ГБ);
- декод: `ink2_route` → `zc.stage(idx)` → те же `gemv_indexed_dense` / `_acc` по таблицам
  пар (`iota`), alpha и вес маршрута — по настоящему `idx`. Шаг целиком на карте и пишется в
  CUDA-граф; при смене `ZC_GENERATION` граф переснимается;
- префилл: групповой GEMM по таблицам zc (`gemm_grouped_dense_rows`). Порядок сегментов —
  сначала эксперты, уже лежащие в слотах (`ZcLayer::slot_owners`), одной группой, затем
  промахи группами по числу слотов: подкачка вытесняет только тех, чей GEMM уже стоит в потоке.
  Без этого циклический проход по 128 экспертам при 98 слотах давал бы почти ноль попаданий.

Переключатели: `SYN_INKLING2_EXPERTS=resident|zc`, `SYN_INKLING2_ZC_SLOTS=N` (слотов на
слой вручную), `SYN_INKLING2_ZC_MIN_SLOTS` (8).

Качество (`ink2_kl`, 2048 токенов `llm-eval-mix.txt`, эталон — резидентный режим): zc со 128,
64 и 16 слотами — KL 0,00002, p99 0,0002, топ-1 100 %, перплексия 2,1993 = 2,1993. Это ровно шум
повторного резидентного прогона (тоже 0,00002). Декод (`ink2_long --ref-decode`, 64 шага после
4096 токенов, teacher forcing): KL 0,000002–0,000008, топ-1 64/64 при 128/64/16 слотах
(резидентный против себя — 0,000006).

Короткий контекст (4096 токенов): резидентно — префилл 1233 ток/с, декод 69,5 ток/с; zc 128
слотов — 1152 / 67,7 (попадания на декоде 99,9 %); 64 слота — 782 / 52,0 (89,5 %);
16 слотов — 594 / 32,9 (61,4 %).

**200K** (`examples/ink2_long`, корпус — реальные документы и исходники с диска: md-файлы
synthos/synshell/synmobile/syngui/hexspire/synspeak/syncook/synaptix без дублей, затем
исходники synaptix-core и моделей; в начале — «иголка», вопрос о ней — в конце):

| | |

| режим | zero-copy (авто), 98 слотов из 128 на слой |
| префилл 200 000 токенов | 1131 с, в среднем 177 ток/с (16K — 831, 100K — ~200, 200K — 90 ток/с на участке) |
| попадания в слоты на префилле | 80,3 % |

## Перенос кэша сессии в RAM (`park_to_host` / `unpark_to`)

`ModelCache::park_to_host` переносит в host-RAM KV всех 48 слотов (кольца SWA и линейный KV
полных слотов), состояния четырёх свёрток слота и буферы позиции/токена; `seq_len` не меняется.
Граф декода держит адреса прежних буферов, поэтому он сбрасывается и переснимается на третьем
шаге после `unpark_to`. Ход на припаркованном кэше — ошибка. Фасад (`LlmKvSession::park_to_host`)
вызывает это для вложенной генерации, как у Qwen4Exp.

Тест `crates/synaptix/tests/inkling2_prefix_kv.rs::inkling2_park_unpark_keeps_cache`: ход 1 →
park → unpark → ход 2. Второй ход берёт из кэша весь первый и даёт те же токены, что сессия без
переезда. Контекст 4096: 371 МБ уходят в RAM за 84 мс и возвращаются за 36 мс.

## Квантованный KV полных слотов (MXFP8 / INT8)

KV растёт только у 8 слотов полного внимания: BF16 — 32 КБ на токен (1M — 33 ГБ). Формат
`KvFormat` (`model.rs`): `Bf16`, `Mxfp8` (E4M3 + масштаб E8M0 на 32 канала) и `Int8` (INT8 +
масштаб E8M0 на 32 канала). У обоих квантованных 8,25 бита на элемент, 16,5 КБ на токен. SWA-кольца
всегда BF16, их размер не зависит от контекста. В слоте лежат байты `[nkv, cap, 128]` U8 и масштабы
`[2, nkv, cap, 4]` U8 (k, затем v). Ядрам передаются `a11` (масштабы) и `u11` (формат).

- Запись: `ink2_qkv` квантует по варпу, один варп на блок из 32 каналов. Масштаб — наименьшая
  степень двойки, при которой amax/sc ≤ 448 (E4M3) или ≤ 127 (INT8). Крайние значения не
  насыщаются. Общий `kv_append_quant_mxfp8` движка берёт amax/256 и срезает значения выше 448,
  поэтому здесь его не используем.
- Чтение: `ink2_attn` (декод) деквантует 4 канала лейна, `ink2_attn_fa` деквантует плитку в
  BF16 shared. Значения e4m3·2^k и int8·2^k представимы в BF16 точно, поэтому дальше считается
  ровно как на BF16-кэше.
- Выбор при загрузке: BF16, пока «KV BF16 на ctx + запас + минимум слотов zero-copy» помещается
  в свободную VRAM; иначе MXFP8. Вручную — `SYN_INKLING2_KV=bf16|mxfp8|int8`.

Тест `tests/kv_quant.rs`. Масштабы минимальны и без насыщения. `ink2_attn` и `ink2_attn_fa`
на квант-кэше совпадают бит в бит с собой же на BF16-декванте этого кэша (хост-декодер).
Ошибка записи (отн. к норме строки, худшая строка): MXFP8 — k 5,3 %, v 3,6 %; INT8 — k 2,6 %,
v 1,1 %.

Качество. Порядок суммирования здесь даёт заметный шум, поэтому замерен и он: одно изменение
порядка суммы F32 в `ink2_mix_out`, без смены математики.

|---|---|---|---|---|---|---|
| эталон BF16 | — | — | — | 1,6543 | — | — |
| шум (порядок суммы) | 0,00226 | 0,030 | 99,06 % | 1,6528 | 0,00541 | 125/128 |

## Префилл-внимание на тензорных ядрах (`ink2_attn_fa`)

Старое `ink2_attn` на префилле: блок на (токен, голову), скалярные FMA, весь KV на каждый токен
без тайлинга. На 200K слой полного внимания занимал 572 мс на кусок 512 токенов (8 слоёв →
~110 ток/с). Новое ядро — flash-внимание в `inkling2.cu`, mma.sync m16n8k16 BF16 → F32
(sm_80+, на sm_120 проверено):

- блок — 64 запроса одной головы (4 варпа × 16 строк), ключи плитками по 32 (K/V через
  cp.async в shared, ldmatrix / ldmatrix.trans). Части по ключам — `blockIdx.z`, их число
  даёт `kern::attn_fa_splits` (~1024 блока, часть ≥ 1024 ключей, буфер ≤ 64 МБ). Сборка —
  прежний `ink2_attn_merge`; при одной части синк и гейт считаются в самом ядре;
- семантика `ink2_attn` целиком: каузальная маска, окно SWA, кольцо KV (`u10`), позиция с
  карты (`a10`), синк, ×sigmoid(gate);
- bias по расстоянию: на плитку и варп — GEMM [16 строк × 16 каналов r] × [16 × 48 расстояний]
  из среза proj в shared (одна k-ступень mma), таблица в shared варпа, выборка
  `idx = r + 31 − c`. Плитки, где все dist ≥ extent, bias не считают — на длинном контексте это
  почти все плитки полных слоёв;
- точность как у F32-пути: q и p расщеплены на bf16 hi + lo (по два mma), r и proj — тоже
  (три mma). Softmax в F32 по основанию 2 (q и r заранее ×log2e). Важная деталь: P·V каждой
  плитки считается в свежем аккумуляторе и прибавляется к O обычным FMA. Аккумулятор mma
  складывает с усечением, и при накоплении O прямо в mma за 6000 плиток (200K ключей) ошибка
  росла линейно: 6,6·10⁻⁴ отн. против f64. Цепочки для q·k (разбиение аккумуляторов) и третья
  часть q ошибку не меняют — проверено.

Тест `crates/synaptix-models/llm/inkling2/tests/attn_fa.rs` сверяет с `ink2_attn` на случайных
входах (σ логитов 3): полные слои и SWA с кольцом и без, T = 1…512, past до 200 000, dist у
границ extent и окна, 1–64 частей. Худшая строка: абс. 3,7·10⁻⁵, отн. 7,8·10⁻⁵, косинус ≥ 0,99999999.
Против f64 на CPU (выборочные строки): новое 0,8–2,8·10⁻⁵ отн., старое 1–2,5·10⁻⁶. Вход `wo`
всё равно округляется в BF16 (2⁻⁹ ≈ 2·10⁻³), то есть разница на два порядка ниже шага BF16.

почти каждый выбор — промах. 1M: KV BF16 —
32,8 ГБ, на 24 ГБ не влезает даже без экспертов. С MXFP8 KV (~8,25 бит) — ~17 ГБ + 4 ГБ весов,
под слоты и активации остаётся ~1,5 ГБ.
